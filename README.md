# 結婚相談所LP 納品物ドキュメント

**`index.html` 1ファイルで完結します。** CSS・JavaScript・写真7点すべてを内包しているため、
このファイルをGitHubにアップロードするだけで公開できます。ビルド作業も画像フォルダも不要です。

`ogp.jpg` は**SNSシェア時のカード画像専用**の1点だけ別ファイルです。
画像はデータURIだとX・Facebook・LINEのクローラーが読み取れないため、これだけ外に出しています。
SNSシェアを使わないなら不要です。使う場合は `index.html` と同じ階層に置いてください。

| ファイル | 必須 | サイズ |
|---|---|---|
| `index.html` | ◎ | 約224KB（写真6点込み） |
| `ogp.jpg` | △ SNSシェア用 | 約97KB |

ページ上では黄色の破線ボックスで表示されるため、置換漏れが目視で分かります。

## 1. 実装方式についての補足

| 項目 | 内容 |
|---|---|
| 実装 | 素のHTML＋CSS＋Vanilla JS（依存ライブラリなし） |
| 理由 | GitHub Pages 等の静的ホスティングにビルドなしで置けるため |
| React/TS/Tailwind版 | 必要であれば同じ構造・同じトークンで変換可能です |
| LP内フォーム | **設置していません** |

フォームを設置していないのは、仕様書26項の「個人情報を安全に管理できない実装の場合は、LP内フォームを作らず、外部予約ページへ遷移させる」に従ったためです。静的ホスティングでは送信内容をサーバー側で安全に受け取れません。
外部予約システム（Google フォーム、TimeRex、Spir、LINE公式アカウント等）を `{{予約URL}}` に設定してください。
LP内フォームが必要な場合は、フォーム専用のバックエンドを用意したうえで追加実装します。

## 7. アクセシビリティ確認結果（WCAG 2.1 AA 相当）

### 満たしている項目
- H1はページ内に1つのみ。見出し階層は h1→h2→h3 の順で飛びなし
- 全画像に内容を説明する `alt` を設定（例：「ネイビーのスーツを着た女性代表カウンセラー」「男性相談者にタブレットを使って説明する女性カウンセラー」）
- 装飾用SVG・記号にはすべて `aria-hidden="true"`
- FAQは `<button>` ＋ `aria-expanded` / `aria-controls` / `role="region"`。**Tab・Enter・Spaceで開閉可能**、初期状態はすべて閉
- ハンバーガーは `aria-expanded` ＋ **Escapeキーで閉じる**
- フォーカスリングを3pxで明示（濃紺セクション上ではゴールド）
- 「本文へスキップ」リンクをフォーカス時に可視化
- 色だけで情報を区別していない（向き不向きは見出し文言＋アイコン形状で区別）
- CTAは `<a>`、開閉ボタンは `<button>` とHTML要素を正しく使い分け
- `prefers-reduced-motion: reduce` に対応（アニメーションとスムーススクロールを無効化）
- 事例カルーセルは自動再生なし、`tabindex="0"` でキーボードスクロール可能

### コントラスト実測（背景色ごと）
| 前景／背景 | 比 | 判定 |
|---|---|---|
| 本文 #33404D ／ #FFFFFF | 9.6:1 | AAA |
| 補足 #66727E ／ #FFFFFF | 4.9:1 | AA |
| 補足 #66727E ／ #F4F6F8 | 4.6:1 | AA |
| CTA文字 #122A43 ／ ゴールド #D5A62F | 6.3:1 | AA |
| ゴールド #D5A62F ／ 濃紺 #122A43 | 6.3:1 | AA |
| 白文字 ／ 濃紺 #122A43 | 16.8:1 | AAA |
| フッター #C3D2DF ／ #122A43 | 9.3:1 | AAA |

### 注意点（1点）
仕様書7項が指定する **CTAホバー時（背景 #B98A18 ＋ 白文字）は 3.1:1** で、通常サイズ文字のAA基準（4.5:1）を下回ります。
仕様を優先して実装していますが、通常時は 6.3:1 を確保しています。厳密にAAを通す場合は、ホバー時も文字を `#122A43` のままにするのが最も簡単な解決です。

なお、補足色 #66727E はペールブルー #EAF2F8 上では 4.35:1 と基準を下回るため、ペールブルー背景の注釈は本文色 #33404D または白カード内に配置しています。

## 8. 表示速度上の注意点

### 現状
| 項目 | 値 |
|---|---|
| `index.html` | 約 283KB（CSS・JS・写真7点込み・gzip前） |
| うち写真 | 約 155KB（WebP実体）→ base64で約207KB |
| 外部リクエスト | Google Fonts のみ（画像は0リクエスト） |
| JavaScript | 依存ライブラリ0。約6KB相当 |

### 単一ファイル化のトレードオフ
- **速くなる点**：画像リクエストが7本→0本。ヒーロー画像はHTMLと同時に届くのでLCPに有利です。
- **遅くなる点**：`loading="lazy"` が効かなくなり、下部の写真6点（約100KB）も最初にダウンロードされます。
- GitHub Pagesはgzip配信されるため、実転送量は約240KB程度です。低速回線を重視するなら、画像を `images/` フォルダに分離して `loading="lazy"` を戻す構成のほうが有利です。

### 実施済みの対策
- 全画像をWebP化。`width` / `height` を明示して**レイアウトシフトを防止**
- フォントは `display=swap` ＋ `preconnect`。ウェイトは Noto Sans JP 4種・Inter 3種に限定
- 自動再生動画・カルーセル・カウントアップなし
- アニメーションは `opacity` / `transform` のみ（レイアウト再計算なし）

### 公開時に確認したいこと
1. **フォントが最大のブロック要因**です。LCPが2.5秒を超える場合は、Noto Sans JPのウェイトを400・700・800の3種に減らすか、フォントファイルをセルフホストしてください。
2. ヒーロー画像は860px幅で書き出しています。モバイルでの実表示は約330pxなので、さらに詰めたい場合は440px版に差し替えると効果的です。
3. 目標値：LCP 2.5秒以内／CLS 0.1未満／INP 200ms以内。CLSは寸法指定済みのため、ほぼ0で通る見込みです。

CTAには `data-cta` 属性が付いており、クリック時に `window.dataLayer` へpushされます。`gtag` があれば同時に送信します。

| イベント名 | 発火場所 |
|---|---|
| `cta_header` | ヘッダー／モバイルメニュー |
| `cta_hero` | ファーストビュー |
| `cta_after_problem` | 問題の原因セクション末尾 |
| `cta_after_method` | メソッドセクション末尾 |
| `cta_pricing` | 料金セクション |
| `cta_consult` | 無料診断セクション（仕様書の一覧にない追加分） |
| `cta_final` | 最終CTA |
| `cta_mobile_sticky` | モバイル固定CTA |
| `cta_footer` | フッターのお問い合わせ |
| `faq_open` | FAQを開いたとき（質問文をパラメータ付与） |

`form_start` / `form_submit` はLP内フォーム未設置のため未実装です。外部予約ページ側で計測してください。

### 流入元の判別
`utm_source` `utm_medium` `utm_campaign` `utm_term` `utm_content` `gclid` `fbclid` `twclid` `ttclid` `yclid` を予約URLへ自動で引き継ぎます。
さらに `lp_cta=（CTA名）` を付与するため、**どのCTAから予約されたか**が予約ページ側で判別できます。

広告出稿時のURL例：
```
https://（公開URL）/?utm_source=x&utm_medium=cpc&utm_campaign=konkatsu_2026aug
https://（公開URL）/?utm_source=instagram&utm_medium=cpc&utm_campaign=konkatsu_2026aug
```

## 12. GitHub Pages での公開手順

1. GitHubで新しいリポジトリを作成
2. **Add file → Upload files** で `index.html` をドラッグ＆ドロップ（SNSシェアを使うなら `ogp.jpg` も一緒に）
3. **Commit changes** をクリック
4. Settings → Pages → Source を `main` ブランチ / `/ (root)` に設定
5. 1〜2分後に `https://（ユーザー名）.github.io/（リポジトリ名）/` で公開されます
6. 公開URLを `{{公開URL}}` に記入して再アップロード

`{{ }}` の書き換えは、GitHub上でファイル名をクリック→鉛筆アイコン（Edit this file）から直接できます。
ただし写真が埋め込まれているぶんファイルが長いので、**編集画面の検索（Ctrl+F / ⌘+F）**を使うと目的の箇所にすぐ飛べます。

## 20. アクセス解析の設定（v9で追加）

### 手順は1つだけ：`index.html` の先頭にIDを入れる

`<head>` の中、上のほうに次のブロックがあります。使いたいツールのIDを書き込むだけで動きます。
**空欄のままなら外部スクリプトは一切読み込まれません**（速度への影響もゼロ）。

```js
var LP_ANALYTICS = {
  ga4Id:     '',   // 例: 'G-XXXXXXXXXX'  … Googleアナリティクス4
  gtmId:     '',   // 例: 'GTM-XXXXXXX'   … Googleタグマネージャー（GA4と併用しない）
  clarityId: ''    // 例: 'abcdefghij'    … Microsoft Clarity（ヒートマップ・録画）
};
```

### どれを入れればいいか

## 31. 「3つの要素」セクションについての検討結果

marriage002 にあった「婚活を前へ進めるには、3つの要素が必要です。」のセクション（出会いの機会 × 選ばれるための準備 × 関係を育てる力）について、**現行LPへの追加は見送りを推奨**します。**未実装です。**

### 見送りを推奨する理由

**1. 結論部分が、すでに同じ文言でLPに存在します**

IBJネットワークセクションの締めに、次の一文があります。

> IBJが出会いの機会を広げ、アコードが選ばれる準備と、会った後の関係づくりを支援します。

これは3要素セクションの締めとほぼ同一です。同じ結論を2回言うことになります。

**2. 3要素のうち2つは、すでに「悩みのタイプ」で提示済みです**

- 出会いの機会 → CASE「出会いの段階で止まっている」
- 関係を育てる力 → CASE「関係づくりの段階で止まっている」

読者は既に自分の位置を選んだあとなので、同じ分類をもう一度見せられる形になります。

**3. 説明セクションが4つ続くことになります**

現在は 悩みのタイプ → 問題の原因 → IBJネットワーク と、解決策に入る前に3つの説明が並んでいます。ここに4つ目を挟むと、Before/Afterまでの距離がさらに伸びます。デスクトップで約19,000px、スマホで約30,000pxある長いページなので、前半の説明を増やすのは離脱リスクが上がります。

### ただし、1つだけ拾う価値があります

3要素のうち**「選ばれるための準備」だけは、現行LPに独立した居場所がありません。** 写真・服装・プロフィール・申込み方針は、料金の説明（初期費用が高い理由）まで下がらないと出てきません。

そこで、**新セクションは作らず、かけ算の式だけを1本の帯としてIBJネットワークセクションの締めと差し替える**案を提案します。

```
婚活の前進 ＝ 出会いの機会 × 選ばれるための準備 × 関係を育てる力
        （IBJ）        （アコード）      （アコード）
```

- 追加される高さは約80px（新セクションなら約700px）
- 「選ばれるための準備」が中盤で提示されるため、後半の初期費用の説明が腑に落ちやすくなります
- 既存の締め文と入れ替えるので、重複は発生しません

実装をご希望でしたらお知らせください。

## 32. かけ算の帯を実装（v19）

IBJネットワークセクションの締めにあった一文を、**3要素のかけ算を表す帯**に差し替えました。**新しいセクションは作っていません。**

### 差し替え前後

**変更前**
> IBJが出会いの機会を広げ、アコードが選ばれる準備と、会った後の関係づくりを支援します。

**変更後**
```
              婚活の前進 ＝

  [ 出会いの機会 ]  ×  [ 選ばれるための準備 ]  ×  [ 関係を育てる力 ]
      IBJ                アコード              アコード

    IBJが出会いの機会を広げ、アコードが残りの2つを支援します。
```

### 設計の意図

- **各項目の下（スマホでは横）に担当をチップで表示**しました。「IBJ／アコード／アコード」と並ぶことで、**アコードの担当が2/3である**ことがひと目で伝わります。文章で読ませるより速く、印象にも残ります。
- **かけ算（×）にしたのは意図的です。**足し算だと「どれか1つでも足りていれば前に進む」と読めますが、かけ算なら**1つでもゼロなら結果はゼロ**という含意になります。「出会いは増えたのに進まない」という読者の実感と一致します。
- 締めの一文は残しました。「×」「＝」は装飾として `aria-hidden` にしているため、**スクリーンリーダー利用者に結論が伝わるようにする**役割も兼ねています。

### レイアウト

| 画面幅 | 表示 | 帯の高さ |
|---|---|---|
| 768px以上 | 横3列。項目名の下に担当チップ | 約246px |
| 767px以下 | 縦3段。項目名と担当チップを1行に収めて圧縮 | 約371px（375px時） |

新セクションとして追加した場合は約700px増えるところ、**差し替えのため実質の増加は約100〜230px**に収まっています。

### 副次的な効果

「選ばれるための準備」という言葉が中盤で登場するようになりました。これにより、後半の料金セクションで説明している**「初期費用が高い理由（写真・服装・プロフィール）」が、伏線を回収する形**になります。

## 35. オンライン実施への不安に対応（v22）

「結婚相談所＝対面」というイメージを持つ人が、他社と比較したときに抱く2つの疑問に答えました。

- 完全オンライン指導で成婚できるのか
- オンライン指導はどう行われるのか（ツール・所要時間）

変更前は「オンライン」という語が5箇所にあるものの、**どう実施されるかを説明した箇所が1つもありませんでした。**

### 追加した5箇所

| 場所 | 内容 |
|---|---|
| 関係構築改善サイクルのリード | 「面談も模擬お見合いも、Google Meetを使ったオンラインで行います。実際にお相手と会うお見合いとデートは、これまでどおり対面です。」 |
| 実績セクションの対象条件 | 「**指導はすべてオンラインで行いました。**」を追記 |
| 料金「支援の範囲」 | **定期面談**に「1回60分から90分」を追記。**実施方法**（Google Meet／対面との組み合わせ可）と**模擬お見合い・会話練習**（オンライン実施、33項目で採点）の2行を新設 |
| FAQ（新設・Q6） | 「**オンラインだけで成婚できますか？**」 |
| 無料診断のチェック項目 | 「オンライン対応」→「**オンライン（Google Meet）**」 |

### 答え方の設計

「オンラインでも大丈夫です」では、疑っている人は納得しません。**前提のズレを解く**構成にしています。

> そもそも、お相手と会うお見合いもデートも対面です。オンラインなのは、その前後の準備と振り返りの部分です。

こう置くと、「オンラインで成婚できるのか」という問い自体が成立しなくなります。オンラインなのは*相手と会う部分*ではなく*準備と振り返りの部分*だからです。

そのうえで、**オンラインを弱点ではなく利点として提示**しています。

> 移動がないぶん、細かく回せます。お見合いの翌日に振り返る、送る前のLINEの文面を確認する、といった支援は、対面を前提にすると成立しません。

そして最後に**実績で裏づけ**ます。20数名・半数以上という数字がすべてオンライン指導によるものだという事実は、この論点における最強の証拠です。FAQの冒頭と実績セクションの2箇所に置きました。

### 配置の優先順位

FAQは検討後半にあり、そこまで到達しない人もいます。そこで**料金セクションの「支援の範囲」を第一の置き場**にしました。608,000円という金額を見た直後に「で、どう提供されるのか」の答えがある形です。ここが離脱の起きやすい地点です。

### 未記載の情報

- 模擬お見合いの所要時間（伺っていないため記載していません）
- 対面を組み合わせる場合の追加費用の有無（発生する場合は追記が必要です）
